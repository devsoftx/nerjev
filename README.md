# nerjev

A TypeScript console app that reads a PDF, extracts named entities and the relationships
between them with TypeSafe's Jev model, and loads the result into Neo4j. A Claude judge
grades the extraction, and a benchmark records tokens, latency, cost and payload size for
every API call. The design is in [spec_v1.md](spec_v1.md).

## Setup

Needs Node 20.12 or newer and, for the graph stage, Docker.

```sh
npm install
cp .env.example .env        # then fill in TYPESAFE_API_KEY and ANTHROPIC_API_KEY
docker compose up -d        # local Neo4j on bolt://localhost:7687, browser on http://localhost:7474
```

`.env` is gitignored. The Neo4j password defaults to `nerjev-local` in both
`docker-compose.yml` and the app; set `NEO4J_PASSWORD` to change it in both places at once.

## Use

Run the CLI with `npm run nerjev -- <command>`, or `npm run build` once and use
`node dist/cli.js <command>`.

| Command | What it does |
| --- | --- |
| `run <pdf>` | PDF to graph. `--cypher out.cypher` writes a script and needs no database |
| `extract <pdf>` | Stages 1 to 5 only; writes JSON under `out/<runId>/` |
| `load <runDir>` | Load an existing run into Neo4j. Loading twice changes nothing |
| `gold` | Score the extractor against `bench/gold/` by exact match. No judge, costs a fraction of a cent |
| `eval <runDir>` | Grade a run with the Claude judge; writes `judge.jsonl` and `accuracy.json` |
| `judge-check` | Check the judge against the gold labels and against known-bad extractions |
| `bench` | Variants × documents × repetitions, cache off. `--judge` adds judged accuracy |
| `report <benchDir>` | Rebuild a benchmark's report from its saved data, with no API calls |
| `dashboard <benchDir>` | Build a self-contained HTML dashboard of a benchmark. `--notes` adds findings and caveats, `--judge-check` adds the judge's calibration |
| `inspect <pdf> --chunk N` | Print the exact Jev request for a chunk, to paste into the TypeSafe Playground |

Try it on the bundled sample, which is fictional text generated by `npm run sample-pdf`:

```sh
npm run nerjev -- run bench/docs/sample-newsletter.pdf
```

Useful flags on `run` and `extract`: `--schema <file>`, `--chunk-size <n>`, `--no-resolve`,
`--accept <p>` and `--review <p>` (confidence thresholds, default 0.70 and 0.40),
`--include-review`, `--no-cache`, `--json`, `--with-mentions`.

## How it works

Jev answers typed questions and does not generate text, so code proposes candidates and
Jev judges them:

1. **Tag.** One Choice per word: which kind of entity is this word part of, or none?
2. **Assemble.** Code merges adjacent words of one kind into spans.
3. **Resolve.** For each span, Jev picks the exact boundary from verbatim candidate
   phrases. Then, in a second request, it types the phrases that survived. The order
   matters: "Dubai" is a location, and "Dubai Supply Chain Expo" is an event.
4. **Merge.** Code pairs names that could be the same entity ("Tanaka", "Aiko Tanaka");
   Jev scores each pair as different, unsure or same, and only "same" merges.
5. **Relate.** For each pair of entities in one sentence, Jev picks a relation the schema
   allows for their types, with its direction, or none.

Everything extracted is a verbatim span with a page number, and every graph edge stores
the sentence that supports it. Entity and relation types live in
[schema/default.schema.json](schema/default.schema.json). Jev reads those descriptions
literally, so they are the main tuning surface: say what is not part of a name as well as
what is.

## What the first benchmark showed

Sample PDF (3 pages, fictional), `jev-1.13.0`, judged by `claude-opus-5`, 2026-09-19.
Full tables: [bench/results/2026-09-19-sample/report.md](bench/results/2026-09-19-sample/report.md).

| | default pipeline (`resolve-80`) |
| --- | --- |
| Extraction wall time | 1.4 s for 3 pages, about 129 pages per minute |
| Extraction cost | $0.0099 per document, $0.0033 per page |
| API calls and tokens | 21 calls, 236k input tokens |
| Payload | 843 KiB sent and received for 2 KB of text |
| Latency per call | p50 150 to 400 ms depending on stage |
| Entities, exact match on gold | 55 right, 0 wrong, 0 missed |
| Relations, exact match on gold | 35 right, 0 wrong, 4 missed |
| Relations, judged on the PDF | 35 right, 0 wrong, 4 missed |
| Entities, judged on the PDF | 66 right, 1 wrong boundary ("Fjord X1 warehouse robot") |
| Confidence calibration error | 0.012 |
| Judge cost | $0.32 per document, about 30 times the extraction it grades |
| Judge check | 94 of 94 verdicts agree with the gold labels; all known-bad extractions caught |

Read these with three cautions. The gold set is 12 short fictional passages, the sample
PDF is built from the same passages, and the prompts were tuned against them. These are
development numbers, not a held-out test, and real documents will score lower. The four
missed relations all need coreference ("The carmaker is owned by…"), which v1 leaves out
on purpose. And the payload is large because every word gets its own question carrying
the full list of entity kinds: about 460 input tokens per word. That is cheap at Jev's
price and fast because questions run in parallel, but it is the first thing to optimize
if volume grows.

Chunk size barely mattered on this document. A 160-word chunk still splits into requests
of about 80 questions to stay under Jev's 64k-token request limit, so it saves no calls.

## What a real document showed

A 15-page IMF board paper on EU sanctions regulations, same models, judged on every third
chunk. Tables: [bench/results/2026-09-19-imf/report.md](bench/results/2026-09-19-imf/report.md);
the interactive version is `bench/results/2026-09-19-imf/dashboard.html`.

| | default pipeline (`resolve-80`) |
| --- | --- |
| Extraction | 10.1 s and $0.094 for 15 pages: 204 calls, 2.23M input tokens, 7.7 MiB of payload |
| Entities, judged | 66 right, 8 wrong, 40 missed: precision 89.2%, recall 62.3%, F1 73.3% |
| Where the misses come from | 31 of the 40 were found but scored 0.40 to 0.70 and held for review; 1 was missed outright |
| Same verdicts, accepting at 0.50 | precision 91.6%, recall 82.1%, F1 86.6% |
| Calibration error | 0.175, against 0.021 on the sample: Jev is under-confident here |
| Relations | 1. The default schema describes companies and people, not regulations |
| Rate limiting | 6 of 2,699 Jev calls hit a 429; all succeeded on retry |
| Judge | 115 calls, $4.31, against $1.18 for all Jev calls in the benchmark |

The run also exposed three bugs, fixed afterwards with tests: a slash joined two names
("Al-Qaida/ISIL"), a name could start with a preposition ("of the Council of…"), and a
hyphen at a line break left a gap ("Al- Qaida"). Still open: American-style dates split at
the comma, and this kind of document needs its own schema.

## Layout

```
src/pdf, src/text        PDF text, normalization, sentences, tokens, chunks
src/jev                  Jev client wrapper: batching to the token budget, cache, call records
src/ner                  tag, assemble, resolve
src/entities             blocking, pair alignment, clustering
src/relations            pair candidates, classification, aggregation
src/graph                statement builder, Neo4j store, .cypher export
src/eval                 judge, rubric, metrics, gold set, judge check
src/bench                recorder, pricing, runner, report
src/telemetry            the fetch wrapper that times and sizes every HTTP attempt
bench/gold               hand-labelled passages        bench/pricing.json   price table
bench/docs               benchmark PDFs                bench/results        saved reports
assets                   the dashboard's HTML template
```

## Tests

`npm test` runs 57 offline tests. Jev is replaced by a fake injected through the SDK's
`fetch` option, so the real client, retry logic and telemetry all run. They cover token
offsets, chunking, span assembly, boundary candidates, entity merging, relation options,
Cypher safety (document text never reaches a query string), metrics, pricing, retries and
caching.

## Extending the gold set

Add passages from your own documents to `bench/gold/*.json`. List each distinct entity
once, exactly as written in the text, with its type; name relation endpoints by those
same strings. `npm run nerjev -- gold` prints every false positive and miss. Include
passages with no entities at all: they are what catches over-extraction.
